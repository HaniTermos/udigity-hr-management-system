## 7. Security observations (no secret values reproduced)

1. **2FA bypass** in any non-production environment, and production status depends on `NODE_ENV` being set (C1). Highest priority.
2. **Fail-open config defaults** in `config/index.ts`: `env` defaults to development, which also enables the bypass and verbose 500 messages. A hard-coded fallback `SESSION_SECRET` exists (unused today, but misleading). Defaults for DB user and empty password are also there.
3. **Session token** is stored in plaintext in `sessions.token` (a DB read gives live sessions), returned in the login JSON body, and accepted as `Bearer`. Together these remove the benefit of the HttpOnly cookie.
4. **No CSRF token/Origin check, no rate limiting or lockout** on login or 2FA. A 6-digit TOTP can be brute-forced without throttling.
5. **No session rotation** after 2FA (session fixation).
6. **Account-state disclosure**: deactivated accounts get a distinct error code before the password is checked.
7. **Seed and demo credentials in the shipped bundle**: `login/page.tsx:20,133` pre-fills a shared dev password, and `Header.tsx:27-30` has a persona switcher that logs in with that password. `seed.ts` gives all six accounts that password and puts a well-known public TOTP test secret in a code comment. Fine for local dev, but it must be gated out of production builds.
8. **Destructive test**: `auth.api.test.ts` `afterAll` deletes every session from localhost IPs on whatever DB `.env` points to. It needs a dedicated test DB.
9. **Audit**: failures are swallowed, and the failed-login payload stores the submitted email (acceptable). `/readyz` exposes raw DB error text publicly.
10. **Pending-2FA allow-list** uses `startsWith` on `originalUrl` (`auth.ts:131`), so `/api/auth/me…` prefixes also match. Low risk today; use exact route matching.
11. Positive: helmet enabled, bcrypt, parameterized SQL throughout, per-request account re-check, deactivation revokes sessions, Zod on auth inputs.

### 9.3 API contract changes the frontend must adopt

- Login, verify and enroll-confirm responses no longer contain `token`. They return `csrfToken`. `GET /api/auth/me` also returns `csrfToken` and `user.sessionState`.
- Every authenticated `POST`/`PATCH`/`PUT`/`DELETE` (including `2fa/verify` and `logout`) must send the header `X-CSRF-Token: <csrfToken>`. The token can also be read from the cookie `udigity_csrf`. Without it the API answers 403 `CSRF_FAILED`. The current `frontend/src/lib/auth.tsx` does not send this header, so 2FA verify and logout will fail until it does.
- Login returns `twoFactorStep: 'verify' | 'enroll' | null`. Enrollment: `POST /api/auth/2fa/enroll/start` returns `{ secret, otpauthUrl }`; then `POST /api/auth/2fa/enroll/confirm { token }`.
- Reset: `POST /api/auth/password-reset/request { email }` returns 202. Then `POST /api/auth/password-reset/complete { token, newPassword }`; the link has the form `/reset-password?token=…`.
- `PATCH /api/employees/:id/status` requires `version` (from `GET /api/employees`).
